### 1.2 `01_Raw_Footage` — 원본 파일명 유지 (예외 규칙)

> [!CAUTION]
> **`01_Raw_Footage` 안의 클립 이름은 절대 바꾸지 않습니다.** 카메라 · OBS · VR 원본은 장비가 부여한
> 파일명을 그대로 유지합니다 — `C0042.MP4`, `A001_0922AB.mov`, `2026-09-22_19-04-31.mkv`.

임포트 후 리네임은 다음 두 가지 사고의 가장 흔한 원인입니다.

| 사고 | 리네임이 원인이 되는 이유 |
| --- | --- |
| **미디어 링크 유실 (Missing Footage, "Where is the file…?")** | 프로젝트 파일은 파일명을 포함한 **경로**를 저장합니다. 클립 이름을 바꾸면 다섯 명 모두의 링크가 끊기고, 200개 클립을 수동으로 다시 연결하는 데 반나절이 듭니다 |
| **프록시 짝 깨짐** | Premiere · Resolve 는 프록시와 원본을 **파일명으로** 짝지웁니다. 한쪽 이름이 바뀌면 프록시가 조용히 떨어져 나가고, 편집이 원본 해상도로 되돌아가거나 아예 연결되지 않습니다 |
| **사이드카·메타데이터 짝 깨짐** | `.xmp`, `.THM`, `.LRV` 사이드카와 분할 기록된(spanned) 클립도 확장자를 제외한 이름으로 짝지어집니다 |

따라서 날짜 · 프로젝트 · 출처 정보는 **폴더명**이 담당하며, 형식은
`[YYMMDD]_[Project]_[Source]` 입니다. 링크를 하나도 건드리지 않고 정렬·검색에 필요한 정보를 그대로 얻습니다.

```text
✅ 01_Raw_Footage/260922_CommunityDay_CamA/C0042.MP4
❌ 01_Raw_Footage/260922_CommunityDay_Interview_CamA_v0.1.MP4
```

프록시는 `01_Raw_Footage/260922_CommunityDay_CamA/Proxies/` 에 두며, **원본과 같은 이름**을 씁니다.

### 1.3 파일이 단계별로 이동하는 흐름

```text
00_Scripts_Board → 01_Raw_Footage → 05_Project_Files → 06_Project_Exports
                                                              │ 승인
                                                              ▼
                                                       07_Final_Output
                                                              │ 프로젝트 종료
```

## 2. 파일 명명 규칙

### 2.1 기본 형식

```text
[YYMMDD]_[Project]_[Note]_[etc.]_[Version].[ext]
```

```text
260922_CommunityDay_RoughCut_1080p_v0.2.mp4
│      │             │        │     │    └── 확장자, 항상 소문자
│      │             │        │     └─────── 버전 (§3)
│      │             │        └───────────── [etc.] — 선택 수식어
│      │             └────────────────────── 이 파일이 무엇인지
│      └──────────────────────────────────── 프로젝트명
└─────────────────────────────────────────── 날짜, YYMMDD (2026-09-22)
```

| 필드 | 필수 | 규칙 | 좋은 예 | 나쁜 예 |
| --- | --- | --- | --- | --- |
| `YYMMDD` | ✅ | 6자리, 0 채움, **연도 먼저**. 파일을 **만든** 날짜 | `260922` | `092226`, `26-09-22`, `9월22일` |
| `Project` | ✅ | 한 덩어리, `PascalCase`, ASCII 만. 프로젝트 내내 같은 표기 유지 | `CommunityDay` | `community day`, `커뮤니티데이` |
| `Note` | ✅ | 파일의 *정체*: `MainEdit`, `RoughCut`, `Master`, `LowerThird`, `Interview` | `MainEdit` | `edit2`, `final` |
| `etc.` | ⬜ | 선택 수식어 0개 이상: 해상도, 카메라, 언어, 라우드니스, 플랫폼 | `1080p`, `CamA`, `KO-sub`, `-14LUFS`, `YT` | `new`, `fix`, `real` |
| `Version` | ✅ | `v<major>.<minor>`, 소문자 `v` (§3) | `v0.2`, `v1.0` | `v2`, `ver1`, `V1.0` |
| `ext` | ✅ | 소문자, 손으로 바꾸지 않음 | `.mp4` | `.MP4` |

반드시 지킬 규칙:

- **`_` 는 필드 구분, `-` 는 한 필드 안의 단어 연결.** `KO-sub` 은 한 필드, `KO_sub` 은 두 필드입니다.
- 공백, 한글, `( ) [ ] { } # % & / \ * ? : " < > |` 금지 — 드라이브는 허용하지만
  Premiere · ffmpeg · 셸 스크립트가 깨집니다.
- **프로젝트가 현재 참조 중인 파일은 리네임하지 않습니다.** 출력하거나 다른 이름으로 저장하세요.
- 이 절 전체의 유일한 예외는 `01_Raw_Footage` (§1.2) 입니다.

### 2.2 왜 `YYMMDD` 인가 — 그리고 혼용 금지

`YYMMDD` 는 **팀 전체의 유일한 날짜 표준**입니다. 6자리 형식 중 **이름순 정렬이 곧 날짜순 정렬**이 되는
유일한 형태이기 때문입니다. 자릿수가 큰 단위(연) → 작은 단위(일) 순으로 배열되기 때문입니다.

| | `YYMMDD` ✅ **우리 표준** | `MMDDYY` ❌ |
| --- | --- | --- |
| `2026-09-22` | `260922` | `092226` |
| 이름순 = 날짜순 | ✅ | ❌ |
| 같은 연도끼리 모임 | ✅ | ❌ |
| 같은 월끼리 모임 | ✅ | ❌ |
| 25년 12월 1일 / 26년 1월 1일 / 26년 9월 22일 정렬 | `251201`, `260101`, `260922` — 정상 | `010126`, `092226`, `120125` — 뒤섞임 |

> [!WARNING]
> **두 형식을 섞는 것은 어느 한쪽만 쓰는 것보다 나쁩니다.** `092226` 과 `260922` 는 둘 다 그럴듯한
> 6자리 숫자이므로, 섞인 폴더는 읽기·정렬·스크립트 처리가 모두 불가능해집니다. 게다가 `090112` 같은 이름은
> 해석 자체가 갈립니다 — 한쪽 규칙에서는 2009-01-12, 다른 쪽에서는 2012-09-01 입니다. 예전 `MMDDYY` 이름을 발견하면 **손대는 그 자리에서
> `YYMMDD` 로 고치세요** — 단, 프로젝트가 참조 중인 파일은 예외 (§2.1).

이 한 가지 규칙 위에 나머지가 모두 올라갑니다.

- 드라이브에서 **이름순**으로 정렬하면 그대로 시간순입니다 — *수정 날짜* 로 바꿀 필요가 없습니다.
- 드라이브 검색창에 `2609` 를 넣으면 한 달, `26` 을 넣으면 한 해가 나옵니다.
- 스크립트와 `ls | sort` 의 결과가 화면에서 보이는 순서와 일치합니다.

<details>
<summary>예전 <code>MMDDYY</code> 이름 변환하기 (먼저 미리보기)</summary>

`sh` 가 아니라 **`bash`** 로 실행하세요(부분 문자열 확장은 bash 전용입니다). 실행할 명령만 출력하고
아무것도 바꾸지 않습니다. 월 `01`–`12`, 일 `01`–`31`, 연 `24`–`30` 으로 읽히는 접두사만 변환 대상으로
제시하므로, 이미 `YYMMDD` 인 이름은 건드리지 않습니다.

```bash
for f in [0-9][0-9][0-9][0-9][0-9][0-9]_*; do
  d=${f%%_*}; rest=${f#*_}; mm=${d:0:2}; dd=${d:2:2}; yy=${d:4:2}
  if (( 10#$yy >= 24 && 10#$yy <= 30 && 10#$mm >= 1 && 10#$mm <= 12 && 10#$dd >= 1 && 10#$dd <= 31 )); then
    echo "mv -- '$f' '$yy$mm${dd}_$rest'"
  else
    echo "# 이미 YYMMDD 이거나 판단이 불확실함, 그대로 둠: $f"
  fi
done
```

출력된 줄을 모두 확인하고, 해당 파일을 참조하는 프로젝트가 없음을 확인한 뒤 `| bash` 를 붙여 다시 실행합니다.

</details>

## 3. 버전 관리

시맨틱 버저닝을 미디어 팀에 맞춘 방식입니다. 항상 두 자리를 씁니다.

| 단계 | 번호 | 위치 | 의미 |
| --- | --- | --- | --- |

| **편집자 A** | 배정된 `05_Project_Files` 프로젝트, `06_Project_Exports` | `00`–`04` |

`07_Final_Output` 에 쓰는 사람은 리드뿐입니다. 그래야 `v1.0` 이 의미를 유지합니다.

### 4.2 프로젝트 패키징 — 미디어 링크 유실 방지

프로젝트 파일은 미디어가 아니라 **경로**를 저장합니다. 누군가의 바탕화면을 가리키는 경로는 나머지 네
대의 컴퓨터에서 아무것도 찾지 못합니다.

> [!IMPORTANT]
> **링크를 걸기 전에:** 미디어는 이미 공용 드라이브의 `01_Raw_Footage`, `03_Graphic_Assets`,
> `04_Audio_Library` 안에 있어야 합니다. `~/Desktop`(바탕화면), `~/Downloads`(다운로드), 휴대폰 전송 폴더, SD 카드에서
> 직접 임포트하지 마세요.

프로젝트를 다른 사람에게 넘기거나 아카이브할 때:

| 프로그램 | 작업 | 참고 |
| --- | --- | --- |
| **Premiere Pro** | `파일 ▸ 프로젝트 관리자 ▸ 파일 수집 후 새 위치로 복사` | *사용하지 않는 클립 제외*, *오디오 conform 파일 포함* 체크. 마스터에는 *변환* 옵션 끄기 |
| **After Effects** | `파일 ▸ 종속성 ▸ 파일 수집…` (*소스 파일 수집: 모든 컴포지션*) | 함께 생성되는 `.txt` 보고서도 같이 전달 |
| **Blender** | `파일 ▸ 외부 데이터 ▸ 상대 경로로 만들기` 후 아카이브 전 `리소스 팩` | `.blend` 가 너무 커지면 프로젝트 폴더로 언팩 |
| **DaVinci Resolve** | `파일 ▸ 미디어 관리`(복사) 또는 `.drp` 아카이브 내보내기 | 로컬 사본이 아니라 드라이브 경로로 재연결 |
| **공통** | 상대 경로만 사용, 가능하면 모든 컴퓨터에서 같은 마운트 지점·드라이브 문자 사용 | 기대 경로를 프로젝트 `README.txt` 에 기록 |

여기서 따라오는 규칙:

- **프로젝트가 링크한 미디어는 이동·리네임하지 않습니다.** 다음 단계로 복사(§1.3)하고 의도적으로 재연결합니다.
- 프로젝트 폴더마다 `README.txt` 한 줄: 결과물, 현재 작업 파일, 미디어 위치.
- **프로젝트 종료 시 패키징은 무조건** 합니다 — 1년 뒤에 열리지 않는 `99_Master_Archive` 항목은
  아카이브가 아닙니다. 패키징한 사본을 한 번 열어 재연결을 확인하세요.
- 공동 편집은 **프록시**(§1.2)로 합니다. 재연결이 작은 파일만 건드립니다.

### 4.3 디스코드 Check-in / Check-out

구글 드라이브에는 **파일 잠금 기능이 없습니다.** 두 사람이 같은 `.prproj` 를 저장하면 조용히 충돌 사본이
생기고, 한 사람의 오후가 사라집니다. 그래서 `#media-checkin` 에서 **사회적으로** 잠급니다.

> [!IMPORTANT]
> **열기 전에 Check-out, 저장하고 닫을 때 Check-in.**

```text
🔒 CHECK-OUT  260922_CommunityDay_MainEdit_v0.3.prproj
              @editor-a · 약 2시간 · ETA 18:00 KST

🔓 CHECK-IN   260922_CommunityDay_MainEdit_v0.4.prproj
              @editor-a · 색보정 완료, 다음 작업: 자막
              → 출력: 260923_CommunityDay_RoughCut_1080p_v0.2.mp4
```

| 규칙 | 내용 |
| --- | --- |
| **한 파일에 한 명만 쓰기** | 체크아웃된 파일은 **읽기 전용**으로 열거나 기다립니다. "금방 고치는 것" 도 예외 없음 |
| **프로젝트당 스레드 하나** | 한 프로젝트의 이력 전체를 하나의 디스코드 스레드에 남깁니다 |
| **ETA 필수** | ETA 없으면 잠금도 없습니다. 나머지가 일정을 짜야 합니다 |
| **최대 점유 24시간** | 그 이후에는 편집 중이라도 체크인하거나, 새 ETA로 잠금을 다시 공지합니다 |
| **응답 없는 잠금(24시간)** | 리드가 강제 해제할 수 있습니다: 파일명과 점유자를 적어 `⚠️ FORCE-RELEASE` 공지 |
| **출력 중에는 동기화 일시 중지** | 렌더가 끝난 뒤 동기화를 재개하고, 그다음 체크인합니다 |
| **체크인은 새 버전을 명시** | 체크인 메시지의 버전 번호가 나머지 네 명에게는 사실상의 기준입니다 |
| **자산도 체크아웃 대상** | `02_Official_Templates`, `03_Graphic_Assets` 는 다섯 명 공용 — 같은 절차를 따릅니다 |

> [!TIP]
> `00_Scripts_Board` 의 대본은 예외입니다. 실제로 다중 사용자 편집이 되는 **구글 문서**로 유지하고,
> `.docx` 사본을 내보내지 말고 링크를 공유하세요.

### 4.4 미디어 캐시와 드라이브 용량 관리

> [!WARNING]
> **미디어 캐시는 공용 드라이브에 두지 않습니다.** 캐시는 컴퓨터별로 생기는 일회성 데이터이면서
> 용량이 거대합니다. 동기화하면 할당량을 태우고 아무도 읽지 않는 충돌 사본만 쌓입니다.

| 프로그램 | 설정 위치 | 설정 값 |
| --- | --- | --- |
| Premiere Pro | `환경 설정 ▸ 미디어 캐시` | **로컬 SSD** 경로 (예: `D:\PrCache`, `~/Library/Caches/PrCache`) |
| Premiere Pro | `미디어 캐시 관리` | *30일보다 오래된 캐시 파일 자동 삭제*, 용량 상한 지정 |
| After Effects | `환경 설정 ▸ 미디어 및 디스크 캐시` | 로컬 디스크 캐시 20–60 GB, 매월 *디스크 캐시 비우기* |
| Blender | `환경 설정 ▸ 파일 경로 ▸ Temp` | 로컬 임시 경로 |
| Drive for desktop | 동기화 방식 | 드라이브 **스트리밍**, 현재 프로젝트만 *오프라인 사용 가능* 표시 |

매월 정리 — 리드가 주관하고 전원이 참여합니다.

- 30일 이상 지난 캐시와 프로그램 자동 저장 폴더를 정리합니다.
- `06_Project_Exports` 를 솎아냅니다: 마지막 `v0.x` 두 개와 픽처 록본만 남기고 삭제.
- 드라이브 저장 용량 페이지를 확인합니다. **80%** 를 넘으면 아카이브 작업을 시작합니다.
- `05_Project_Files` 에 60일 이상 방치되었으면서 아카이브 계획이 없는 프로젝트가 없는지 확인합니다.

용량 규칙:

- **드래프트는 H.264 `.mp4`.** ProRes · DNxHR 은 `07_Final_Output` 과 `99_Master_Archive` 에만 둡니다.
- **카메라 원본은 콜드 스토리지.** 드라이브에는 프록시와 셀렉트만 두고, 카드 전체 이미지는 아카이브
  드라이브(사본 2개, 1개는 외부 보관)에 두고 프로젝트 `README.txt` 에 위치를 적습니다.
- **같은 자산을 두 벌 두지 않습니다.** 프로젝트 폴더로 복사하지 말고 `03_Graphic_Assets` ·
  `04_Audio_Library` 를 링크하세요.
- 드라이브 충돌 사본(`… (1)`, `Copy of …`)은 생긴 날에 지웁니다 — 어느 쪽이 진짜인지 확인한 뒤에.
